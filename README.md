# CANTranslator

_Generates the C++ CAN message API (CANApi) used by the DUSC telemetry board firmware. The API is generated from one spreadsheet that lists every CAN message on the vehicle. The current output is CANApi v1.0-beta.4, which is used by the `nick-22Library` branch of Telemetry2021. Documented Nov 2026._

## System overview

```
 config/CANConfig.xlsm   (one row per CAN message: CAN ID, length, byte names, data types, byte order)
   │  Excel VBA functions build the C struct for each row (ApiGen/excelMacroModule.vba)
   ▼
 python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h CANApi/CanApiv10
   ▼
 CANApi/CanApiv10.hpp, CanApiv10.cpp   (generated: message structs, CAN ID macros, dispatch switch)
 CANApi/CANHelper.hpp, CANHelper.cpp   (hand-written: MCP2515 wrapper, read() and send())
   │  committed to the DUEM/CANApi repository (git submodule here, at CANApi/)
   ▼
 Telemetry2021 firmware, Telemetry/src/CANApi submodule
   │  Telemetry/UseMsgList.hpp chooses which messages are compiled in
   ▼
 Arduino Mega 2560 telemetry board
```

* [ApiGen/README.md](ApiGen/README.md): the generator (running it, what it generates, `USE_MSG_` macros, using the API in firmware)
* [config/README.md](config/README.md): **the CAN message spreadsheet**: what each column means, the data type syntax, and how to add or change a message

This repository used to decode the raw hex logs from the board's SD card as well. That moved to the Telemetry2021 receiver in June 2024, so nothing here decodes data any more.

## CANApi versions

| CANApi | Generated files | Generated by | Used by (Telemetry2021 branch) |
|---|---|---|---|
| `8d050b1` (Aug 2023, merged as `v0.4`) | `CanApiv04.hpp/.cpp` | the earlier `translator/Translator.py`, removed in Nov 2024 (still in git history before commit `d126975`) | `PERI-DEVELOPMENT-TPB-1126`, `ESC-CODE` |
| `fe308f7` (Jun 2024, `v1.0-beta.4`) | `CanApiv10.hpp/.cpp` | [ApiGen/CanApiGen.py](ApiGen/CanApiGen.py) | `nick-22Library` |

The two versions are **not source compatible**. v0.4 has one struct per message deriving from `CANMsg` (e.g. `Telemetry::_TimeAndFix`) and a free `processMessage()` function. v1.0 has plain structs in a union, a `CANHandler` class and `processMessage()` member functions, and it needs a value on every `USE_MSG_` macro (see [ApiGen/README.md](ApiGen/README.md#choosing-messages-usemsglisthpp)).

Running the generator on the committed [config/CANConfig.xlsm](config/CANConfig.xlsm) reproduces CANApi `v1.0-beta.4` exactly (checked Nov 2026; the only difference is one leading space, removed from the generator in commit `4b1304b`).

## First-time setup

```shell
git clone --recurse-submodules git@github.com:DUEM/CANTranslator.git
cd CANTranslator
python3 -m venv ~/virtualenvs/cantranslator
source ~/virtualenvs/cantranslator/bin/activate
pip install openpyxl
```

If `CANApi/` is empty, the submodule has not been fetched. Run `git submodule update --init` (**not** `--remote`, see [Known limitations](#known-limitations)).

You only need Python and openpyxl to run the generator. To **edit** the spreadsheet you need Microsoft Excel (Windows or macOS) with macros enabled. See [config/README.md](config/README.md#editing-the-spreadsheet).

## How to add or change a CAN message

1. Edit the message's row in [config/CANConfig.xlsm](config/CANConfig.xlsm) in Excel ([config/README.md](config/README.md) explains every column). Check the generated `c struct` cell (column U) shows a struct, not `#VALUE!`.
2. **Save in Excel.** The generator reads the values Excel saved for the formula cells; it does not calculate them itself.
3. Bring the CANApi submodule up to date and generate into it:
   ```shell
   git -C CANApi switch main
   git -C CANApi pull
   python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h CANApi/CanApiv10
   ```
   `-h` is the output path **without** an extension: it writes `CanApiv10.hpp` and `CanApiv10.cpp`, overwriting them. The script prints every spreadsheet row as it goes and ends with `c++ files generated file generated`.
4. Check that only what you expected changed:
   ```shell
   git -C CANApi diff
   ```
5. Test it by building the firmware (Telemetry2021, `nick-22Library` branch) with the new files. To use the new message there, add it to `Telemetry/UseMsgList.hpp` (see [ApiGen/README.md](ApiGen/README.md#choosing-messages-usemsglisthpp)).
6. Commit and push in CANApi (and tag it if it is a release), then update the submodule pointer in this repository and in Telemetry2021:
   ```shell
   git add CANApi config/CANConfig.xlsm
   git commit -m "Add <message> to CAN config"
   ```
7. Update the Telemetry2021 DBC files so the receiver can decode the message.

Never edit `CanApiv10.hpp` or `CanApiv10.cpp` by hand: the next run of the generator overwrites them. `CANHelper.hpp/.cpp` in CANApi are hand-written and are not touched by the generator.

## Known limitations

**Generator and spreadsheet**
* The generator reads the values **Excel saved** in the formula columns. If the workbook is saved by a program that cannot run its VBA functions (or is saved with macros disabled), those cells hold errors or old values, and the generated code is wrong without any warning.
* The `Active/Confirmed` column is **ignored**: every row above the `END` row is generated. Which messages are compiled is chosen in the firmware's `UseMsgList.hpp` instead.
* The command-line options are unusual: `-h` is the output file, not help, and the usage message printed for a bad option lists `-i` and `-o`, which do not exist.
* If a data type is invalid or the bytes do not add up to the DLC, the VBA functions are meant to return a message starting `ERROR`. Because they use `Return` instead of `Exit Function`, Excel shows `#VALUE!` instead. The generator does not check for either.

**Message and field names**
* Names are made by removing everything except letters (`CamelCase` in the VBA), so **digits are lost**: `Testbed enviroCAN.ino1` and `...ino2` both become `TestbedEnvirocanIno`. The names for `Velocity`, `Rail_15V` and `Rail_3_3VAnd1_9V` are typed in by hand to work around this.
* Some names are duplicated: Testbed `TestbedEnvirocanIno` (0x1B1, 0x1B2), Tritium `Reserved` (0x60A, 0x60D), Orion `CellVoltages` (0x6B0, 0x700) and Orion `CellTempsDischargeChageCurrentLimit` (0x6B1, 0x701, 0x702). The 0x702 struct also has two fields called `Blank`. **Enabling any of these in `UseMsgList.hpp` gives a compile error.** None of them are enabled on `nick-22Library`.
* Typos in the spreadsheet are part of the API: `Tritium::StausInformation`, `Orion::CellTempsDischargeChageCurrentLimit`. The Telemetry2021 DBC files renamed `StausInformation` to `StatusInformation` in Nov 2026, so the firmware and receiver names now differ.

**Big-endian (Orion BMS) messages**
* For rows marked `BIG`, the generated dispatch code calls `reverseBytes()` (in CANApi's `CANHelper.cpp`) before casting. As written in v1.0-beta.4 it swaps `data[i]` with `data[dlc - i]` for every `i`, which swaps most pairs twice. The overall effect is that `data[0]` is exchanged with the byte after the payload, and nothing else changes.
* Even a correct reversal of the whole payload would reverse the **order of the fields** as well as the bytes within each field, so multi-field messages such as 0x6B0 would still be decoded wrongly. Each field needs its own byte swap.
* This does not affect the telemetry board: it does not enable any Orion messages, and `processAll()` gets the frame unchanged.

**Struct layout**
* The structs rely on the compiler adding **no padding** between fields, which is true for the AVR (Arduino Mega). On a 32-bit board (ARM, ESP32) a `uint16_t` after a `uint8_t` is padded, so messages such as Orion 0x6B0 would not line up with the CAN data. `__attribute__((aligned(8)))` only aligns the start of the struct.

**Repository**
* [.gitmodules](.gitmodules) says `branch = dev`, but the pinned commit is on CANApi `main`, and CANApi's `dev` branch is older (`4650ce0`). `git submodule update --remote` would therefore go **back** to an older API. Use `git submodule update --init`, or `git -C CANApi switch main` as above.
* [ApiGen/CANHelper.hpp](ApiGen/CANHelper.hpp) and [.cpp](ApiGen/CANHelper.cpp) are an older copy of the files in CANApi. They have no include guard, include `CanApiDraft.hpp`, define `LATEST_MSG_ID` twice (the second should be `LATEST_MSG_DLC`) and have no `reverseBytes()`. Use the CANApi copies.
