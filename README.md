# CANTranslator

_Generates the C++ CAN message API (CANApi) used by the DUSC telemetry board firmware. The API is generated from one spreadsheet that lists every CAN message on the vehicle. It produces CANApi v1.0 (`src/generated/CanApi.hpp/.cpp` in CANApi; `CanApiv10.hpp/.cpp` before the Nov 2026 restructure), the version used by the `nick-22Library` branch of Telemetry2021. Documented and fixed Nov 2026._

## System overview

```
 config/CANConfig.xlsm   (one row per CAN message: CAN ID, length, byte names, data types, byte order)
   │  Excel VBA functions build the C struct for each row (ApiGen/excelMacroModule.vba)
   ▼
 python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h CANApi/src/generated/CanApi
   │  checks the spreadsheet first; writes nothing if anything is wrong
   ▼
 CANApi/src/generated/CanApi.hpp, .cpp   (generated: message structs, CAN ID macros, dispatch switch)
 CANApi/src/CANHelper.hpp, .cpp          (hand-written: MCP2515 wrapper, read() and send())
   │  committed to the DUEM/CANApi repository (git submodule here, at CANApi/)
   ▼
 Telemetry2021 firmware, Telemetry/src/CANApi submodule
   │  Telemetry/UseMsgList.hpp chooses which messages are compiled in
   ▼
 Arduino Mega 2560 telemetry board
```

* [ApiGen/README.md](ApiGen/README.md): the generator (running it, its checks, what it generates, `USE_MSG_` macros, using the API in firmware)
* [config/README.md](config/README.md): **the CAN message spreadsheet**: what each column means, the data type syntax, and how to add or change a message

This repository used to decode the raw hex logs from the board's SD card as well. That moved to the Telemetry2021 receiver in June 2024, so nothing here decodes data any more.

The v0.4 and v1.0 APIs are **not source compatible**. v0.4 has one struct per message deriving from `CANMsg` (e.g. `Telemetry::_TimeAndFix`) and a free `processMessage()` function. v1.0 has plain structs in a union, a `CANHandler` class and `processMessage()` member functions (see [ApiGen/README.md](ApiGen/README.md)).

`CANApi/src/generated/CanApi.hpp/.cpp` must always be exactly what the generator produces from [config/CANConfig.xlsm](config/CANConfig.xlsm). The tests check this.

## First-time setup

```shell
git clone --recurse-submodules git@github.com:DUEM/CANTranslator.git
cd CANTranslator
python3 -m venv ~/virtualenvs/cantranslator
source ~/virtualenvs/cantranslator/bin/activate
pip install -r Tests/requirements-test.txt     # openpyxl for the generator, plus pytest
```

If `CANApi/` is empty, the submodule has not been fetched: run `git submodule update --init`.

You only need Python and openpyxl to run the generator, and `g++` for the tests that compile the generated code. To **edit** the spreadsheet you need Microsoft Excel (Windows or macOS) with macros enabled. See [config/README.md](config/README.md#editing-the-spreadsheet).

## How to add or change a CAN message

1. Edit the message's row in [config/CANConfig.xlsm](config/CANConfig.xlsm) in Excel ([config/README.md](config/README.md) explains every column). Check the `c struct` cell (column U) shows a struct, not `#VALUE!`.
2. Press **Ctrl+Alt+F9**, then **save in Excel**. The generator reads the values Excel saved for the formula cells; it does not calculate them itself (but it does check them, see below).
3. Bring the CANApi submodule up to date and generate into it:
   ```shell
   git -C CANApi switch main
   git -C CANApi pull
   python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h CANApi/src/generated/CanApi
   python3 ApiGen/CanApiGen.py -c config/CANConfig.xlsm -h ApiGen/generatedAPIs/test
   ```
   `-h` is the output path **without** an extension: it writes `.hpp` and `.cpp` files, replacing any already there. The script lists each message and ends with `Generated ...`. If it finds a problem in the spreadsheet (a duplicate name or CAN ID, sizes that do not add up to the DLC, a value Excel has not recalculated, ...) it lists the problems and writes **nothing**. Fix them in Excel and run it again.
4. Run the tests, and check that only what you expected changed:
   ```shell
   pytest
   git -C CANApi diff
   ```
5. Test it by building the firmware (Telemetry2021, `nick-22Library` branch) with the new files. To use the new message there, add it to `Telemetry/UseMsgList.hpp` (see [ApiGen/README.md](ApiGen/README.md#choosing-messages-usemsglisthpp)).
6. Commit and push in CANApi (and tag it if it is a release), then update the submodule pointer in this repository and in Telemetry2021:
   ```shell
   git add CANApi config/CANConfig.xlsm ApiGen/generatedAPIs
   git commit -m "Add <message> to CAN config"
   ```
7. Update the Telemetry2021 DBC files so the receiver can decode the message.

Never edit `CanApi.hpp` or `CanApi.cpp` by hand: the next run of the generator overwrites them (both start with a `GENERATED FILE: DO NOT EDIT` notice). `src/CANHelper.hpp/.cpp` in CANApi are hand-written and are not touched by the generator.

## Testing

```shell
pytest
```

[Tests/test_canapigen.py](Tests/test_canapigen.py) checks that:

* the committed spreadsheet passes all the generator's checks
* `CANApi/src/generated/CanApi.*` and `ApiGen/generatedAPIs/test.*` are exactly what the spreadsheet generates
* the generator catches each kind of spreadsheet problem (using small made-up spreadsheets)
* the generated API, with **every message enabled**, compiles with `g++` together with CANApi's `CANHelper` and a stub of the MCP2515 library ([Tests/stubs/mcp2515.h](Tests/stubs/mcp2515.h)), and decodes test frames correctly: little-endian and big-endian (signed and unsigned) messages, unknown IDs, `processAll()` getting the frame unchanged, `reverseBytes()`, and `USE_MSG_` macros with no value

The compile tests use the laptop's compiler, not `avr-gcc`, so they do not replace building the firmware for the board. They are skipped if `g++` is missing or the CANApi submodule is not checked out.

## Changes made in November 2026

These fixes change the generated API, so firmware moving to it from CANApi `v1.0-beta.4` may need updating. The Telemetry2021 `nick-22Library` firmware uses none of the renamed messages.

| Change | Before | After |
|---|---|---|
| Rows marked `N` in `Active/Confirmed` are no longer generated | all rows | Testbed 0x1B1, 0x1B2 and Tritium 0x60A, 0x60D left out |
| Tritium 0x601 renamed (typo) | `Tritium::StausInformation` | `Tritium::StatusInformation` |
| Orion messages given unique names (several shared a name, so could not be enabled) | 0x6B0, 0x700 `CellVoltages`; 0x6B1, 0x701, 0x702 `CellTempsDischargeChageCurrentLimit` | 0x6B0 `PackParametersDefaultId`, 0x6B1 `CellTempsDclDefaultId`, 0x700 `PackParameters`, 0x701 `CellTempsDcl`, 0x702 `CellVoltages` (the 0x7xx names follow the Telemetry2021 DBC files) |
| Orion 0x702 fields renamed (two were called `Blank`) | `Blank`, `Blank` | `BlankA`, `BlankB` |
| Testbed rows renamed (both were `TestbedEnvirocanIno`) | | `TestbedEnvirocanTempHumidity`, `TestbedEnvirocanHeatIndexLight` |
| Big-endian (Orion) messages: each field is byte-swapped, in a copy | whole payload passed to the broken `reverseBytes()`, in place | `processMessage()` gets the correct values; `processAll()` gets the frame as received |
| Structs are `packed` | `aligned(8)` only | `packed, aligned(8)`: same layout on any compiler (no change on the AVR) |
| `USE_MSG_X` defined with no value | compile error | struct only (like `0b01`) |
| `CANHelper::reverseBytes()` fixed | swapped most bytes twice, and one byte past the payload | reverses the `can_dlc` bytes |
| 0x111 field names `Spare1` to `Spare3` typed into the spreadsheet | formula, which would have become `Spare` three times on the next recalculation | typed values, so they stay `Spare1` to `Spare3` |

## Known limitations

**Generator and spreadsheet**
* The generator reads the values **Excel saved** in the formula columns. It checks them against the typed columns and stops if they disagree, but it cannot run the VBA functions itself, so the spreadsheet must still be edited and saved in Excel.
* `-h` means the output file, not help (use `--help`). It is kept so that existing commands still work.
* If a data type is invalid or the bytes do not add up to the DLC, the VBA functions are meant to return a message starting `ERROR`. Because they use `Return` instead of `Exit Function`, Excel shows `#VALUE!` instead. The generator reports either as a problem with that row. Fixing the VBA needs Excel.

**Message and field names**
* Names are made by removing everything except letters (`CamelCase` in the VBA), so **digits are lost**: `Spare 1` becomes `Spare`. Type the name you want over the formula cell, as done for `Velocity`, `Rail_15V`, `Rail_3_3VAnd1_9V` and `Spare1` to `Spare3`. The generator reports any duplicate names this causes.
* Orion 0x702 is described differently here (seven 1-byte values) and in the Telemetry2021 DBC file (`LowCellVoltage` and `HighCellVoltage` as 16-bit values, then `InternalTemperature` and `Blank`). Which is right depends on the Orion BMS profile loaded on the car. Check before enabling it.

**Firmware**
* The generated code has been compiled and tested with `g++` on a laptop, not with `avr-gcc` for the board. Build the firmware before using a new CANApi.
* The fixes are on the CANApi branch `PERI-DEVELOPMENT-TPB-1126-fixes`. The submodule here points at that branch's commit, so **push the CANApi branch before (or with) this repository's branch**, or the submodule cannot be fetched.
